# CLI versions: what each version was tested with, and the evidence

Chorus aims to work with as many versions of each CLI as it can, not only the newest. This page is the record of which
versions were run end to end on a real machine, what passed, and where the captured evidence is. It is generated from the
captures (§3); the doctor's tested list (`docs/doctor.md` §2.1) is read from the same files.

## 1. How a version is tested

`tools/probe/matrix.mjs` runs one version through two layers:

1. **Capture, with the real CLI** (one model turn per scenario; Claude on haiku). The CLI runs in a throwaway git workspace with
   per-session flags only, never the user's config (rule 4):

   | Scenario | What the CLI is asked | Passes when |
   |---|---|---|
   | `hello` | reply with two words | exit 0; a session id and token usage in the stream |
   | `mcp` | call `probe_get_context` on the per-session MCP server | the server is started with the thread id, gets `initialize` and `tools/call`, and the model saw the result (a secret only the tool returns) |
   | `shell` | run `echo chorus-probe-$((6*7))` | exit 0; `chorus-probe-42` in the stream (the prompt only has the arithmetic) |
   | `artifact` | write `.chorus/artifacts/probe/hello.md` | the file exists |
   | `resume` | remember a word, then resume and ask for it | same session id; the word comes back |
   | `envelope` | reply with the code word from its standing instructions, in capitals plus `-OK` | `KUMQUAT-OK` in the stream. The code word is only in the standing note, given through the channel Chorus uses for that CLI: Claude, the MCP server's instructions; Codex, `developer_instructions`; agy, a workspace rules plugin |
   | `approval` | in the interactive TUI, with prompts on, create a file with the shell | the CLI's own permission prompt appears, Enter approves it, the file exists |

2. **Chorus against the capture**: the version's tests in `test/contract/adapters.test.ts` parse that capture with Chorus's own
   code: the stream and transcript adapters (turns, tool calls, results, usage, session id, resume), the MCP tool call, the
   envelope reply, and the approval detector on the captured prompt screen. These tests then stay in `npm test` for good, so a
   later adapter change that breaks an old version fails at once.

A version is:

| Verdict | Meaning |
|---|---|
| ✅ tested | every capture and every Chorus test passed. It goes in the doctor's tested list |
| ⚠ partial | the core (hello, shell, resume) works; something else failed. Usable; the failing part is named |
| ❌ broken | a core capture failed |
| … incomplete | a scenario was not captured (not run, or the CLI can't be pinned) |

## 2. Running it

```bash
node tools/probe/matrix.mjs codex 0.155.0,0.160.0     # pinned installs beside your own codex
node tools/probe/matrix.mjs claude 2.1.290,2.1.300
node tools/probe/matrix.mjs claude installed           # the version on PATH
node tools/probe/matrix.mjs agy installed              # agy can only be probed at the installed version
node tools/probe/matrix.mjs codex --docs-only          # rebuild this page from the captures
node tools/probe/clis.mjs list                         # pinned versions on this machine
```

- **Pinned installs** (`tools/probe/clis.mjs`): each version goes into its own npm prefix under `~/.cache/chorus/clis/<cli>/<version>/`.
  The user's own `claude` / `codex` (native, Homebrew or npm global) is not touched; checked 2026-10-23: after installing Codex
  0.160.0 and Claude Code 2.1.300 pinned, `codex` on PATH still reports 0.163.0 and `claude` 2.1.309. A pinned Claude Code runs with
  `DISABLE_AUTOUPDATER=1` so it can't update the global one. Both reuse the user's login (Claude: `auth status` → logged in).
- **agy** can't be pinned: it updates itself and has no versioned package. Each agy version is captured when it is the installed one.
- A scenario already captured for a version is kept unless `--force`, so committed fixtures don't move under the other tests.
- Evidence per version: `fixtures/<cli>/<version>/<scenario>/` (`command.json`, `stdout.jsonl`, `stderr.txt`, `mcp-log.jsonl`,
  `result.json`, the CLI's own transcript under `home-changes/`; for approval `prompt-screen.txt` and `screen.txt`) and
  `fixtures/<cli>/<version>/matrix.json` (the verdict). Captures are redacted (emails, account ids, the home path); review them
  before committing (rule 6).

## 4. When a version breaks

1. The row names the failing scenario or Chorus test; the capture next to it shows what the CLI did instead.
2. Make the adapter handle both: a version-specific branch only where the format really differs (e.g. Claude 2.1.302's auto mode
   needs `--permission-mode default` to show prompts, 2.1.303 renamed it `manual` but still accepts `default`;
   `docs/integrations/approvals.md`). Keep the older versions' tests green: they are the reason the fixtures are kept.
3. Re-run the matrix for the broken version (`--force`) and one tested version on each side; commit the captures with the fix.
