# `chorus doctor`: setup check, CLI integration tests and issue report (plan)

Status: **proposal**, 2026-10-23. Nothing here is built yet.

Today `chorus doctor` (`src/cli/commands.ts` `doctorCmd`) prints Node, the store path, and for each CLI its version, the version we
verified and the login state; the desktop's Doctor page shows the same lines. This plan turns doctor into the step right after
install.

## 0. The buyer's path

1. **One command** installs Chorus: `curl -fsSL https://chorus-cli.web.app/install.sh | bash`, `brew install --cask chorus`, or
   `npx @chauvoluuhuong/chorus-install`. Nothing else to read or run first.
2. The installer (or the desktop app on first launch) runs the **fast check**: no model calls, **1–5 s** (§2).
3. Each CLI ends in one of four states, and only the last two ask anything of the user:

| State | When | What the user sees |
|---|---|---|
| **Ready** | installed, logged in, and the version is one we tested (§2.1) | `✔ Claude Code 2.1.306: tested, ready`. Then **Continue**. No test runs |
| **Missing** | not on `PATH` | the CLI's page opens in the browser, the install command is shown, and on **Install** Chorus runs it (§3) |
| **Needs login** | installed, not logged in | on **Log in** Chorus runs the CLI's login command (§3) |
| **Untested version** | installed and logged in, version not in the tested list | the deeper integration test runs for that CLI only (§4, about 1–3 min). Pass: `✔ works`, Continue. Fail: offer to install a tested version (§3.2, optional) and to send an issue report (§7) |

So a buyer on tested versions is through in a few seconds; the model turns of the integration test are spent only where a CLI version
is new to us.

**Where the code lives.** The fast check, the tested-versions list, the install table, the suite, the report and the issue code are
part of the private CLI integration library (`docs/chorus-core.md`). Chorus hosts them: the installer step, the desktop popup and
Doctor page (§6), and `chorus doctor`.

**What is tested and what is not.** Our own code (store, MCP server, handoff digest, UI) is covered by `npm test` before every
release; doctor does not test it again. Doctor tests only the **contract between Chorus and each CLI on this machine**: the flags,
files, events, screens and keys Chorus relies on. Those are what break on a buyer's machine: a newer CLI version, another install
method, a different login or plan.

## 1. When it runs

| Entry | What happens |
|---|---|
| `site/install.sh` (curl), `packages/installer` (`npx`), the Homebrew cask | Last step: `chorus doctor --fast` in the terminal when there is a TTY (`< /dev/tty` in the shell script), then the app opens |
| **Desktop app**, first launch, and after an update of Chorus, chorus-core or an installed CLI | The doctor popup opens with the fast check (§6) |
| `npm install -g @chauvoluuhuong/chorus` | No postinstall prompt (npm hides output, no TTY). The first `chorus` run with no `~/.chorus/doctor/last.json` runs the fast check |
| By hand | the desktop's Doctor page, or `chorus doctor` any time; flags in §8 |

## 2. The fast check (no model calls, 1–5 s)

Run for all three CLIs at once; each line below is a process call or a file read, never a model turn.

| Id | What | How | If not met |
|---|---|---|---|
| F1 | Node `>= 22.18` | `process.versions` | Stop. Link to nodejs.org, `brew install node` |
| F2 | CLI on `PATH` | `<cli> --version` (also gives F3) | Missing (§3) |
| F3 | Version tested | look the version up in the tested list (§2.1) | Untested version (§4) |
| F4 | Logged in | `claude auth status` (JSON), `codex login status`; agy has no status command: its settings file plus a sign-in record under `~/.gemini/antigravity-cli` (to verify, rule 1) | Needs login (§3) |
| F5 | Install method | where the binary resolves (`~/.local/bin` native, npm prefix, Homebrew) | recorded for §3.2 and the report; never a failure |

The slowest part is `--version` and the login commands of three CLIs; run in parallel they take about 1–3 s on this Mac (to measure
when built; the target is under 5 s).

### 2.1 The tested list

chorus-core ships, per CLI, the list of versions with full e2e evidence: the versions marked ✅ tested in
`docs/integrations/versions.md` (generated by `tools/probe/matrix.mjs`; each passed every probe scenario and every Chorus contract
test with the real CLI, and its captures are the evidence, `docs/chorus-core.md` §10). The fast check reads it from the installed chorus-core, so a new
chorus-core release can add versions without a Chorus release.

| Installed version | Treated as |
|---|---|
| exactly a tested version | tested: Ready |
| between two tested versions with no known break between them (the list marks breaks) | tested: Ready |
| newer than the newest tested, older than the oldest, or across a known break | untested: deeper test |

A deeper test that passes on this machine is remembered in `~/.chorus/doctor/last.json`, so the same version is Ready next time
here. (It doesn't add the version to the tested list for anyone else: that needs the evidence run in the core repo.)

## 3. Missing CLI, login, and tested versions

### 3.1 Missing or not logged in

```
⚠ Codex CLI (codex) is not installed.
  Chorus works with any one CLI; each extra one adds handoff targets.
  Page:     https://github.com/openai/codex          (opened in your browser)
  Install:  npm install -g @openai/codex@0.163.0     (the newest version we tested)
  Install it now? [y/N]
```

- The CLI's page opens in the browser at once, so the user sees where it comes from.
- `y` runs the install command with the user's terminal attached (the desktop: in a terminal pane, §6), then re-runs F2–F5 for that
  CLI and, if needed, the login command (`claude auth login`, `codex login`, `agy` once to sign in).
- A missing CLI is installed **at the newest tested version** when the install method allows pinning, so it lands Ready.
- Default is **No**. `--yes` never covers installs; only `--install claude,codex` does.
- None of the three installed: say Chorus can't do anything yet.
- Rule 4 holds: the CLI's global config is never touched.

Install commands (each to verify on a clean macOS user per rule 1, then recorded in the core repo's integration docs):

| CLI | Page | Latest | Pinned to a tested version | Status |
|---|---|---|---|---|
| Claude Code | https://docs.claude.com/en/docs/claude-code/setup | `curl -fsSL https://claude.ai/install.sh \| bash` | npm: `npm install -g @anthropic-ai/claude-code@<v>`; native: `curl -fsSL https://claude.ai/install.sh \| bash -s <v>` | npm pin ✅ (`docs/integrations/versions.md`); native pin 📄 |
| Codex | https://github.com/openai/codex | `npm install -g @openai/codex` | `npm install -g @openai/codex@<v>` | ✅ (`docs/integrations/versions.md`); Homebrew can't pin |
| agy | Antigravity download page | ❓ | ❓ agy updates itself; no way to pin is known | ❓ |

### 3.2 Untested version that fails: offer a tested one

```
✖ Codex 0.170.0 is newer than the versions Chorus is tested with, and 1 integration case failed:
    C4 transcript: no rollout carries this chat's marker
  Chorus works with Codex 0.163.0 (tested). Optional:
    npm install -g @openai/codex@0.163.0
  [Install 0.163.0]  [Keep 0.170.0]  [Report issue]
```

- Optional and off by default; **Keep** is always there, and Chorus keeps working with what passed.
- The command depends on how the CLI was installed (F5): npm → npm pin; Claude native → the install script with a version; Homebrew
  → no pin, so the npm command is shown with a note that it installs a second copy.
- After an install, F2–F4 run again and the line goes Ready.
- The CLI may update itself later (Claude Code's native install and agy do). Turning that off is in the CLI's own settings, which
  Chorus doesn't touch (rule 4); the line says so and names the setting.

## 4. The integration suite

One suite of 13 cases, grouped by integration point; same case ids, same prompts, same pass rules for Claude, Codex and agy. Only
the mechanism under test differs per CLI (§4.3). Then the cross-CLI cases (§4.4).

The same suite has two users:
- **The core repo**, on every version it adds to the tested list: the full suite with evidence kept (`docs/chorus-core.md` §10).
- **A buyer's machine**, only for a CLI whose version is untested (§2.1), and only after the user says yes, since it spends model
  turns on their plan.

### 4.1 Rules that keep it clean

1. **Isolated.** Each CLI gets a fresh workspace in the OS temp folder (`git init`, no user files) and a fresh `CHORUS_HOME` there.
   The user's projects and `~/.chorus` are never read or written. Per-session flags only; agy's workspace files
   (`.agents/mcp_config.json`, the rules plugin) go in the temp workspace only.
2. **A nonce per case.** Every case puts a random value where only the mechanism under test can carry it (the thread id, a
   seeded thread title, a skill file, a file the agent wrote). A pass can't come from an earlier run, from the prompt or from
   the model guessing.
3. **Judged on facts, not on wording.** Pass rules check files on disk, parsed events, the virtual screen and the store. A reply
   is only checked for the nonce.
4. **One thing per case.** A case fails for one reason. Cases that build on another (C4 and C5 use C3's session) are skipped with
   `needs C3` when it fails, so one break doesn't show up as four.
5. **Known model randomness gets one retry**, reported as `✔ on retry` (Codex only asks for approval when the model escalates;
   C10 and C13 depend on the model following the envelope). Nothing else is retried.
6. **Login and quota are not failures.** An auth or plan-limit message (the `AUTH` regex in `test/smoke/run.ts`, plus the
   plan-limit texts once TD-10 is captured) stops that CLI's column with `needs login` / `out of quota`.
7. **Cheapest settings**: `--model haiku` for Claude, low effort for Codex and agy. Stdin closed for headless runs, the parent
   Claude env vars removed (rule 5). Each case has a timeout (headless 120 s, PTY 90 s).
8. **Evidence for every case**, pass or fail: the exact command line (redacted), stdout, stderr, the final virtual screen for PTY
   cases, and the workspace file list. Copied into the report folder, then the temp workspace is deleted (`--keep` keeps it).
9. The test sessions are left in the CLI's own history (`~/.claude/projects`, `~/.codex/sessions`, agy `brain/`). Doctor
   doesn't delete in the user's CLI folders; the report lists their session ids.

## 6. Desktop: the doctor popup and the Doctor page

### 6.1 When the popup opens

- First launch: no `~/.chorus/doctor/last.json`.
- Something changed since the last run: the Chorus version, the chorus-core version, or the version of an installed CLI (read with
  `--version` at start, as the app does now). A CLI newly installed or removed counts.
- Never otherwise: no popup on a normal start. The Doctor page in the sidebar foot runs it any time.

It opens over the window as soon as the page loads, with the fast check (§2), which is done in a few seconds. When every CLI is
Ready the popup says so and closes itself after 2 s (or on **Continue**). For an untested version it asks before the deeper test
(the turns are on the user's plan); **Continue** is always there, the test keeps running behind, and its result goes to the
Doctor page and to a dot on the sidebar's Doctor button (amber while running, red with the count of failures, none when all pass).

### 6.2 What it shows

```
┌ Checking your agents ─────────────────────────────────────────────────┐
│ C  Claude Code  2.1.306         ✔ Tested, ready                       │
│ X  Codex        0.170.0         ◌ New version · testing 4 of 9        │
│      Chorus is tested with 0.163.0; checking that 0.170.0 works.      │
│ A  agy                          ⚠ Not installed                       │
│      [Install]  [Open page ↗]                                         │
│                                                                       │
│                                           [Stop test]  [Continue]     │
└───────────────────────────────────────────────────────────────────────┘
```

One row per CLI. The status is what the user needs to act on, in this order:

| Row state | Shows | Actions |
|---|---|---|
| Tested, ready | ✔ | — |
| Not installed | the command (pinned to the newest tested version, §3.1) | **Open page** opens the CLI's page in the browser. **Install** opens a terminal pane in the popup (a PTY over the WebSocket `chorus serve` already uses for agent screens) running the command, so the user sees and answers it; on exit the row checks again |
| Needs login | the login command | **Log in**: the same terminal pane with `claude auth login` / `codex login` / `agy` |
| New version | the tested version next to it | **Test it** (the deeper test, with its turn count) · **Skip** |
| Testing | `n of 9`, the case running | — |
| Works | ✔ `0.170.0 works on this Mac` | — |
| Problem | ✖ and the one-line reason of the first failed case | **Install 0.163.0** (optional, §3.2) · **Keep** · **Details** (the case, its reason, the command, the stream tail or final screen) · **Report issue** |
| Out of quota | ⚠ and the reset time when the CLI says it | — |

### 6.3 The Doctor page

Replaces today's text-only page (`doctorHtml` in `src/desktop/app.js`): the matrix of §5 as a table (cases down, CLIs across, the
groups A–E and X as sections), the time of the last run and the versions it ran on, and **Check again** (fast), **Run full test**,
**Report issue** (when something failed) and **Show report folder**. A running test fills in live; clicking a cell shows its
details.

### 6.4 Report issue in the desktop

A dialog with the redacted `issue.md` (§7) in an editable text box, the list of evidence files in the zip, and:
**Create issue with GitHub CLI** (only when `gh` is logged in), else **Open on GitHub** (title in the URL; body copied to the
clipboard; zip shown in Finder), and **Cancel**. Nothing is sent before one of the first two is clicked.

### 6.5 What `chorus serve` adds

| Route | What |
|---|---|
| `GET /api/doctor` | prerequisites, the last report, and `due` (whether the popup should open) |
| `POST /api/doctor/run` `{ level, agents }` | starts a run; progress as `doctor` messages on the WebSocket (the runner's events, `docs/chorus-core.md` §4) |
| `POST /api/doctor/stop` | stops it; finished cases keep their result |
| `POST /api/doctor/terminal` `{ agent, action: 'install' \| 'login' }` | a PTY with the command from the install table; nothing else can be run through it |
| `GET /api/doctor/issue` · `POST /api/doctor/issue` `{ body, via: 'gh' \| 'browser' }` | the redacted body; sends it the chosen way |

These sit behind the local API's existing token (`docs/phase5.md` §2).

### 6.6 Before building

The popup, its row states, the Doctor page and the report dialog go into a mockup first (`docs/mockups/`, the desktop's look),
and the build is compared with it scene by scene. The desktop e2e proof (`npm run proof:desktop`) gets new steps: a fresh
`CHORUS_HOME` opens the popup and every tested CLI is Ready in under 5 s; a CLI hidden from `PATH` shows Not installed with its
command; a CLI shown as an untested version runs the deeper test with real Claude and Codex; a forced failure shows Problem, offers
the tested version and opens the report dialog.

## 7. Issue report when something failed

If any case is ✖ (warnings, skips, `needs login` and `out of quota` alone don't ask):

```
2 cases failed. Create an issue report so we can fix it? [y/N]
```

On yes:

1. **Build** `issue.md`. Title per failure fingerprint: `doctor: codex 0.170 C4 transcript`. Body: chorus version and install
   method, OS name/version/arch, Node, shell, terminal (`TERM_PROGRAM`), each CLI's version, install path and login state
   (yes/no, never the account), the matrix, and for each failure the case, its reason, the command line, and the evidence (stream
   tail, final screen, file list) in collapsed `<details>` blocks, cut to GitHub's 65 536-character limit. The full evidence goes in
   `doctor-report.zip`.
2. **Redact** with the probe's redaction (`tools/probe/probe.mjs`: emails, account ids, home path → `~`) plus keys and tokens
   (`sk-…`, `Bearer …`), then **show the whole body** and ask again: `Send this? [y/N/e=edit]`. Nothing leaves the machine before the
   user has read it.
3. **Send**:
   - `gh` installed and logged in: search open issues for the fingerprint first and offer to comment there; else
     `gh issue create --repo chauvoluuhuong/chorus --title … --body-file issue.md --label doctor`. Print the URL.
   - otherwise: open `https://github.com/chauvoluuhuong/chorus/issues/new?title=…&labels=doctor` with the title only (no logs or personal
     data in the URL), copy the body to the clipboard, and show `issue.md` + `doctor-report.zip` in Finder to paste and attach.
4. The fingerprint (`CLI + CLI minor version + case id`) makes the same failure from many buyers land in one issue, and tells us
   which integration fact in `docs/integrations/` moved.

`chorus doctor --report` re-offers the report for the last failed run without running the suite again.

## 8. Flags

| Flag | Meaning |
|---|---|
| `--fast` / `--deep` / `--full` | level (§4.5); default `--fast`, then `--deep` for untested versions after asking |
| `--agents claude,codex` | limit the CLIs |
| `--cases C3,C7` | run only these cases (and the ones they need) |
| `--install claude,codex` | install these if missing without asking |
| `--yes` | yes to running the suite; never to installs or to sending a report |
| `--keep` | keep the temp workspaces |
| `--json` | machine output |
| `--report` | issue report for the last failed run |

Non-TTY (piped, CI): no prompts, the fast check only unless `--deep` / `--full` is given; never installs or sends.

## 10. How we prove doctor itself (docs/testing.md layers)

- **L1**: each case's pass rule against the committed fixtures (a passing and a failing capture per CLI, from `fixtures/`);
  redaction; `issue.md` building and the 65 536 cut; stable fingerprints.
- **L2** with `tools/fake-agent`: an empty `PATH` gives the install offer; a fake agent that writes no transcript fails C4 and
  skips C5; an auth message gives `needs login`; non-TTY never prompts; a `gh` stub records the issue call.
- **L3** on the Mac: `chorus doctor --full` all green with claude + codex + agy; once more with one CLI logged out.
- **Clean machine**: a new macOS user account, run `install.sh`, see every tested CLI Ready in under 5 s, accept the Codex install, put an
  untested Codex version on `PATH`, see the deeper test run and fail on a forced break, take the tested-version offer, send a report to the issues repo; screenshots in `docs/proof/doctor/`.
- **Desktop**: the new `proof:desktop` steps of §6.6.
